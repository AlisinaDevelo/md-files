# Release Provenance

Every Forge tag is built from the tagged commit by the pinned GitHub Actions release
workflow. The workflow publishes three deterministic host bundles, a hash manifest, and
an SPDX 2.3 software bill of materials (SBOM). The package builder is standard-library
only and rejects untracked bundle files, symlinks, unsupported Git modes, and executable
mode drift.

## Published assets

For release `vX.Y.Z`, the GitHub release contains:

- `forge-X.Y.Z-claude.tar.gz` - Claude Code plugin files.
- `forge-X.Y.Z-codex.tar.gz` - Codex plugin files.
- `forge-X.Y.Z-agents.tar.gz` - `.agents` and Zed-compatible skills plus instructions.
- `forge-X.Y.Z-sbom.spdx.json` - SPDX 2.3 inventory with SHA-256 file checksums and
  runtime dependencies.
- `forge-X.Y.Z-manifest.json` - source commit, tag, version parity, archive inventories,
  attestation contract, and verification contract.
- `SHA256SUMS` - SHA-256 digests for every published artifact except the checksum file
  itself, which would create a circular digest.

SPDX 2.3 is used for compatibility with GitHub's SPDX attestation verification examples;
the [SPDX specification index](https://spdx.dev/use/specifications/) identifies SPDX 3.0
as the current specification family. The release also receives GitHub artifact
attestations: default SLSA build provenance and an SBOM predicate for the archives. See
the [GitHub artifact attestation documentation](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
and the [SLSA v1.2 specification](https://slsa.dev/spec/v1.2/).

## Verify online

Install a current GitHub CLI and verify the archive's workflow provenance:

```bash
gh attestation verify forge-X.Y.Z-claude.tar.gz \
  -R AlisinaDevelo/md-files \
  --signer-workflow AlisinaDevelo/md-files/.github/workflows/release.yml \
  --source-ref refs/tags/vX.Y.Z
```

Verify the SPDX predicate specifically:

```bash
gh attestation verify forge-X.Y.Z-claude.tar.gz \
  -R AlisinaDevelo/md-files \
  --signer-workflow AlisinaDevelo/md-files/.github/workflows/release.yml \
  --source-ref refs/tags/vX.Y.Z \
  --predicate-type https://spdx.dev/Document/v2.3
```

Repeat for the Codex and `.agents` archives. The command checks the signed attestation's
repository and workflow identity; it does not replace inspection of the release commit,
manifest, or source.

## Verify offline

Download the release assets, check out the exact tag for the verifier, and verify the
manifest, hashes, archive contents, and SBOM without network access during verification:

```bash
gh release download vX.Y.Z --repo AlisinaDevelo/md-files --dir forge-release
git clone --branch vX.Y.Z --depth 1 https://github.com/AlisinaDevelo/md-files.git forge-source
python3 forge-source/scripts/verify_release.py \
  --manifest forge-release/forge-X.Y.Z-manifest.json \
  --root forge-release \
  --version X.Y.Z \
  --commit "$(git -C forge-source rev-parse HEAD)"
```

The verifier requires exact artifact names and digests from the manifest, exact archive
member sets and file checksums, an SPDX 2.3 document, and matching SPDX checksums. The
CI job builds the same source commit twice with the same `SOURCE_DATE_EPOCH` and compares
every generated byte.

## Forge attestation contract

Forge's release manifest declares `forge-release-attestation-v1`. Its DSSE payload is a canonical
in-toto Statement v1 with the SLSA provenance predicate `https://slsa.dev/provenance/v1`. The
statement subjects are exactly the three host archives and the SPDX SBOM listed in the manifest.
The binding also covers:

- source repository, commit, tag, and source ref;
- release version and `SOURCE_DATE_EPOCH`;
- the release policy digest and manifest digest;
- the Forge release build type and three resolved input descriptors; and
- the explicit builder identity and deterministic invocation digest.

Forge keeps three evidence profiles distinct:

| Profile | Verification boundary | Trust material |
| --- | --- | --- |
| `local-hmac-v1` | Offline development evidence; symmetric and not public provenance | Explicit local trust root containing the HMAC key |
| `public-key-dsse-v1` | Offline verification of a signed DSSE envelope | Explicit Ed25519 trust root with active, retired, or revoked keys |
| `github-artifact-v1` | Digest-only receipt for a prior `gh attestation verify` result | GitHub/Sigstore verification remains external and host-provided |

Active and retired keys may verify existing evidence; revoked keys fail closed. A trust root may
restrict acceptable builder identities. This is key rotation and verification policy, not a claim
that Forge has a signing authority or that a developer laptop meets a SLSA build level.

Verify a Forge DSSE envelope offline after importing the exact release directory, policy, and
trust root:

```bash
python3 scripts/forge-attestation.py verify-release \
  --envelope forge-release-attestation.json \
  --trust-root trusted-root.json \
  --manifest forge-release/forge-X.Y.Z-manifest.json \
  --root forge-release \
  --policy forge-source/policies/release.json \
  --source-ref refs/tags/vX.Y.Z \
  --builder-id https://github.com/AlisinaDevelo/md-files/.github/workflows/release.yml \
  --json
```

Run the deterministic contract and tamper corpus locally against a built release:

```bash
python3 scripts/forge-attestation.py self-test \
  --manifest forge-release/forge-X.Y.Z-manifest.json \
  --root forge-release \
  --policy policies/release.json \
  --source-ref refs/tags/vX.Y.Z \
  --json
```

The self-test covers subject, predicate, signature, trust-root, policy-binding, and artifact
tampering. Its output contains digests, counts, profiles, and status only; it does not emit raw
release contents, credentials, or provider responses. The local release gate runs this check.

The contract follows the [SLSA v1.2 provenance specification](https://slsa.dev/spec/v1.2/provenance),
the [in-toto envelope layer](https://github.com/in-toto/attestation/blob/main/spec/v1/envelope.md),
and [GitHub's offline artifact-attestation guidance](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline).

## Run the local release gate

When hosted CI is unavailable, run the same release-critical checks locally from a clean
checkout:

```bash
./scripts/local-release-check.sh
```

The gate runs structure validation, tests, static evals, cross-host scenarios, backend and
chaos conformance, Python/Ruff/Markdown/Agent Skills checks, strict Claude and Codex
validation, two byte-identical release builds, offline manifest/SBOM/archive verification,
installed-candidate replay evidence, and isolated Claude/Codex marketplace lifecycle smoke.
It writes the submission evidence report to `${TMPDIR:-/tmp}/forge-local-release-evidence.json`
by default; set `FORGE_LOCAL_RELEASE_EVIDENCE` to choose another path. This is local
evidence, not hosted CI evidence or external directory approval.

## Map an installed file

The manifest's archive `contents` entries are the bridge between a release and an
installed host file. For example, compare a packaged skill with the Codex cache:

```bash
tar -xOf forge-release/forge-X.Y.Z-codex.tar.gz forge/skills/orchestration/SKILL.md | sha256sum
sha256sum "$HOME/.codex/plugins/cache/forge/forge/X.Y.Z/skills/orchestration/SKILL.md"
```

Claude uses the corresponding path under
`$HOME/.claude/plugins/cache/forge/forge/X.Y.Z/`. A matching digest ties the installed
file to the release archive; the manifest then ties that archive to its source commit and
tag.

## Threat model and limits

- **Compromised dependencies:** the packager and verifier use Python's standard library.
  GitHub CLI is host-provided and declared in the SBOM; release actions are pinned to
  reviewed commit SHAs and should be updated through Dependabot and review.
- **Mutable tags or release assets:** the manifest records both tag and commit. Protect
  release tags and review any asset replacement; re-run both attestation and offline
  checks after downloading.
- **Unreviewed generated or executable content:** source inputs must be Git-tracked, and
  generated bundle files must be regular files with derived `100644` or `100755` modes.
  The builder renders only from the reviewed capability graph, rejects symlinks and
  unsupported filesystem entries, and fails on source drift, catalog drift, and version
  mismatch.
- **Keyless signing assumptions:** GitHub artifact attestations provide verifiable
  workflow and repository identity through OIDC-backed signing. They do not prove that
  the source was correct or vulnerability-free; consumers still need source review,
  policy protection, and SBOM analysis.
